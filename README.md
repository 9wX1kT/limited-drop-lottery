# 限量发售抽选系统 · 可验证 Demo

一个不依赖后端的限量发售抽选系统原型：**预约 → 承诺式抽签 → 支付窗口 → 超时按序补位**，全流程可在浏览器内演示，抽签结果可自行复算。

**在线体验**：<https://9wx1kt.github.io/limited-drop-lottery/>（管理入口在 C 端页脚，用于运营侧演示）

> 本项目为个人作品演示，用于产品方法论展示，不构成真实商品销售。

## 核心机制

| 环节 | 规则 |
|---|---|
| 库存 | 限量 50 件 |
| 预约窗口 | 24 小时，超时截止 |
| 去重 | 11 位手机号 + 设备 ID，任一命中即拦截 |
| 抽签 | 对全部有效预约统一计算，无先到先得 |
| 支付窗口 | 中签后 15 分钟内确认，超时释放资格 |
| 补位 | 资格释放后**按抽签排序顺位依次递补，不做二次抽签** |

## 可验证性设计（核心卖点）

- **种子承诺**：`seed = sha256(活动ID | 预约截止时间 | salt)`，salt 在发售公告中提前公布——运营方在看到报名名单后无法更换种子
- **名单指纹**：抽签前公布有效预约名单的哈希指纹，名单不可事后增删
- **结果可复算**：结果公示页提供排序依据，任何人可用相同输入重算并核对中签名单

## 合规设计

依据《盲盒经营行为规范指引（试行）》（国市监稽发〔2023〕39 号）：

- 公示商品种类/样式、抽取规则、商品分布、限量投放数量、抽取概率、商品价值范围（第九条）
- 概率设定与抽取记录留存不少于 3 年（第十条）
- 不向未满 8 周岁未成年人销售；8 周岁以上需监护人同意（第二十三条）

界面同时区分两类数字：**抽取概率**（法定公示项）与**预计中签率**（商业自选项，后台可配置是否公示）。

## 产品决策记录

- **为什么超时后按序补位而不是重抽**：重抽会让"候补"失去意义，也给黄牛留下二次套利空间；按序递补让队列公平且可预期
- **为什么 C 端只显示热度档位而非精确人数**：精确实时人数会诱发"观望到最后时刻再决定"，制造卡点与服务器峰值；因此 C 端降精度、B 端全精度
- **为什么中签率做成开关**：供需接近时公示概率有助于建立信任；头部 IP 严重供不应求时，公示极低概率等于官方劝退转化

## 技术边界（诚实声明）

- 纯前端单文件实现（零依赖），数据存储于浏览器 localStorage，按浏览器隔离
- 设备 ID 为浏览器级标记，非真实设备指纹；无 IP 限流、无服务端鉴权与并发控制
- 生产化改造需要服务端：真实账号体系、幂等接口、并发安全与风控

## 技术

单文件 `index.html`，原生 HTML/CSS/JavaScript，无框架、无外部依赖，可部署至任何静态托管平台。
